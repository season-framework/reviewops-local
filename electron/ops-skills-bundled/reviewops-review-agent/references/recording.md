# Recording a ReviewOps response or development result

Read the original review, relevant replies and existing evidence before responding. Answer the original request directly. Preserve valid prior content, links and attachments and use the same review for the same work; do not create duplicate status replies after a retry. Do not delete another author's content or close a review merely to make a checklist appear complete.

## What changed

Describe the actual changed behavior and how it addresses the request. Keep investigation, implementation, tests, execution and publication separate. A source path or commit is useful only when actually read and relevant. Never claim completed development from an agent start, a plan or a saved review.

## Operations and results

For a meaningful UI result use a four-column Markdown table when comparison helps: `항목 / 조작 / 예상 동작 / 실제 결과`. Start the actual result with `**통과**`, `**오류 발견**`, `**미실행**` or `**부분 완료**` as appropriate, then state the observed behavior. Use a small number of relevant scenarios rather than an unrelated overall test total.

Place actual whole-window photographs in a separate step-by-step flow with readable captions. When annotating, use one or two numbers and outlines on a separate copy without covering labels or state. Explain how photographs from different versions, fixtures or sessions differ; do not present them as a continuous operation. Report missing evidence accurately and never substitute a packaged example.

Only claim actions actually performed. Distinguish source execution from an installed package, synthetic protocol responses from genuine model turns, selected settings from directly observed effective values, and record equality from attachment-byte equality. A selector or fixture failure is not automatically a product defect. Retain failures, partial work and unrun checks.

## Verify the saved response

Use the original review and a stable operation ID. After an uncertain result, lookup the original receipt before retrying. Re-read the saved response, status and attachment metadata and report the actual returned review/result links. Update a factual or formatting mistake in the same authorized result instead of adding duplicate completion comments.

Internal review work does not require GitHub publication or a standalone QA report. Apply those actions only when requested for that destination, and do not claim an unperformed external post or report as complete.
