# Recording a ReviewOps result

Write the concrete changed behavior, the related original request and the verified source/commit. Keep planned, implemented, tested and published states distinct. For UI work use a four-column table: Item / Operation / Expected behavior / Actual result. Put Pass, Fail, Not run or Partial at the start of the actual result. Place whole-window photographs in a separate step-by-step flow, not inside narrow table cells.

Only claim results from actions you actually performed. Distinguish source execution from an installed package, synthetic model/tool responses from genuine model execution, passed settings from observed effective values, and preserved records from observed bytes. Failed selectors or fixtures are not automatically product failures. Keep genuine failures and incomplete checks visible.

Preserve valid prior code, evidence and replies. Update an existing result for the same work instead of adding duplicate status replies. Re-read the saved result and attachments. Do not delete someone else's content or close an issue simply to make a checklist appear complete.
