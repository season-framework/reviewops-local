# GitHub 이슈 관리

문제와 개발 결과를 실제 조작 화면, 검사 내용, 코드 변경과 연결하여 기록한다. 필요한 내용은 빠짐없이 쓰고 반복 설명은 줄인다. 고정된 줄 수로 제한하지 않는다.

## 작업 범위

- 저장소, 이슈 본문, 모든 관련 댓글과 코드를 읽고 작업 범위를 파악한다. 목록과 댓글은 페이지 나누기를 끝까지 조회한다. 새 이슈를 만들기 전에 열린 이슈와 닫힌 이슈에서 같은 문제를 검색한다. 같은 문제가 있으면 기존 이슈를 활용한다.
- 쓰기 작업은 사용자 요청 범위에서 수행한다. 같은 세션에서 이슈 게시나 댓글 정리를 이미 요청했다면 다시 승인받지 않는다. 조사나 초안 작성만 요청했다면 게시하지 않는다. 스킬 사용 자체가 모든 GitHub 변경을 허용하는 것은 아니다.
- 사용할 수 있는 GitHub 도구를 우선 사용하고, 필요한 기능이 없으면 CLI나 API를 사용한다. 인증 정보는 출력하거나 파일·본문·사진에 저장하지 않는다.
- 보고서도 요청받았다면 사용 가능한 [qa-usability-report](../qa-usability-report/SKILL.md) 스킬의 사진과 검사 기록을 재사용할 수 있다. HWPX의 사진 표시는 해당 스킬의 문서 도형 방식을 사용한다. 이슈와 댓글만 작성할 때는 이 스킬과 [작성 양식](references/github-writing.md)으로 진행한다. 다른 스킬의 설치를 필수 조건으로 삼지 않는다.

## 이슈 작성

제목에 문제를 일으키는 상황과 잘못된 동작을 쓴다. 본문에는 문제와 사용자 영향, 재현 조건과 조작 순서, 기대한 동작, 실제 결과를 적는다. UI 문제 설명에 필요한 스크린샷을 포함하고 단계와 사진을 연결한다. 직접 재현하지 않은 제보와 개선 제안은 실행한 검사와 구분한다.

사진이 필요한 UI 문제는 촬영·노출 정보 정리·업로드 확인까지 마친 후 게시한다. 제보에 사진이 없고 재현도 불가능하면 확인한 사실로 초안을 완성하고 부족한 자료를 최종 응답에 명시한다. 무관한 사진이나 다른 실행의 성공 화면으로 채우지 않는다. 사용자가 제한된 제보만으로 등록하도록 명시한 경우에는 그 범위와 미재현 사실을 그대로 적는다.

코드 위치는 실제 읽은 저장소 상대 경로나 GitHub 파일 링크로 표시한다. 확인하지 않은 원인을 추정하여 결함으로 단정하지 않는다. 긴 배경 설명, 요청하지 않은 작업 계획·우선순위·미작업 목록은 제외한다.

## 개발 결과 댓글

- 실제 수정하고 커밋한 내용이 있을 때 개발 결과 댓글을 작성한다. 조사·계획·코드 위치 확인만으로 완료 댓글을 남기지 않는다. 기존 개발 결과를 보완하는 작업이면 해당 커밋과 실행 자료를 읽고 범위 안에서 갱신한다.
- 개발된 항목의 **스크린샷, 조작 시나리오, 세부 작업 결과**를 모두 포함한다. 바뀐 동작, 관련 요구사항, 실제 실행한 조건과 결과, 커밋·코드 링크를 [개발 결과 양식](references/github-writing.md)에 따라 작성한다. 해당 이슈와 무관한 수정이나 릴리즈 전반의 소식은 제외한다.
- GitHub 시나리오 표는 `항목 / 조작 / 예상 동작 / 실제 결과`의 4열로 작성한다. 판정은 실제 결과 앞에 `**통과**<br>`처럼 표시한다. 사진은 별도의 화면 흐름에서 단계 순서로 연결하여 좁은 표 안에 넣지 않는다.
- UI가 없는 서버 기능은 요청·응답, 검사 명령·출력 등 동작을 보여 주는 실제 결과 화면을 촬영한다. 실행 환경과 입력·결과를 설명하고 제품 UI와 구분한다. 단순 테스트 합계, 문서 화면, 꾸민 성공 화면으로 개발된 동작의 사진을 대신하지 않는다.
- 필요한 사진이나 검사 자료가 없으면 해당 완료 댓글을 게시하지 않는다. 확보한 자료와 초안은 정리하고 다른 승인된 작업은 계속한다. 사용자가 사진 없는 결과 기록을 명시적으로 요청한 경우에는 검증한 코드·검사 사실만 기록하며, 화면 검사 통과나 이슈 전체 완료로 표현하지 않는다.
- 실제 작업의 diff, 커밋, 검사 출력으로 문장마다 사실을 대조한다. 개발 완료, 검사 통과, GitHub 닫힘 상태를 구분한다. 부분 수정·미실행·미제공을 전체 통과로 바꾸지 않는다. 실패가 검사 도구의 선택자·시험 자료·실행 환경 때문이면 제품 오류로 단정하지 않는다.
- 소스 실행과 배포 앱, 시험용 응답과 실제 AI 응답, 전달한 설정과 실행 도구가 알린 사용값을 구분한다. 이전 성공 이력으로 이번 조건의 통과를 대신하지 않는다. 기능 오류와 사용성 불편은 별도로 기록한다.
- 해당 동작을 검사한 항목별 결과를 적는다. 전체 검사 합계로 대신하지 않으며 재실행한 검사를 중복 합산하지 않는다. 업데이트 관련 작업은 실제 수행한 버전 전환, 자료 유지, 실패·복구를 각각 기록한다.
- 링크의 커밋이 해당 원격 저장소에 존재하는지 확인한다. 파일 링크는 전체 SHA의 `blob/<commit-sha>/<path>` 주소와 확인한 줄 위치를 사용한다. 원격에 없는 커밋이나 이동하는 브랜치 주소로 완료를 입증하지 않는다. 게시를 위해 임의로 커밋을 푸시하지 않는다.
- 요청하지 않은 작업 계획·우선순위·남은 작업 나열·자기평가·반복 소개는 제외한다. 문구 검토 체크리스트는 GitHub 댓글이 아닌 최종 응답에 둔다.

## 사진과 조작 순서

- 프로그램 전체 창을 보존한다. 메뉴·탭·대상·현재 상태를 알 수 있어야 한다. 확대 사진이 필요하면 전체 창 사진에 덧붙이며 확대 사진만으로 대체하지 않는다. 여러 창의 동작은 해당 창을 모두 보여 주거나 각각 촬영하여 관계를 설명한다.
- 사진은 초기 상태 → 조작 → 결과 순서로 고른다. 같은 실행의 변화가 필요한 주장은 같은 대상·자료의 연속 장면으로 설명한다. 다른 실행이나 다른 조건이면 제목과 설명에 그 차이를 적는다. 실제 개선 전·후 장면이 아닌 사진을 ‘개선 전·후’로 부르지 않는다.
- 중요한 위치에만 번호와 상자를 표시한다. 보통 한 장에 1~2곳을 표시하고, 번호·상자가 서로 겹치거나 버튼·문자·결과를 가리지 않도록 한다. 단계 제목과 사진 아래 설명에서 같은 번호를 사용한다.
- 원본 사진과 실행 기록을 유지하고 표시·가림 처리는 별도 사본에 적용한다. 실제 화면의 글자·값·상태를 생성하거나 고쳐서 결과를 바꾸지 않는다. 본문·사진·터미널 출력의 인증 정보, 개인 정보, 비공개 주소·경로를 점검한다. 필요한 가림 처리는 사실 판단에 필요한 영역을 가리지 않으며 가린 부분을 설명한다.
- 사진을 실제로 열어 전체 창 보존, 글자 판독, 번호 위치, 단계 설명과 관찰 결과의 일치를 확인한다. 이전 사진의 파일명이나 캡션만 보고 재사용하지 않는다.

## 기존 댓글 정리

사용자가 정리를 요청한 댓글만 다룬다. 변경 직전에 댓글 ID, 이슈 번호, 작성자, 기존 본문을 다시 읽고 현재 인증 계정의 글인지 확인한다. 타인의 글은 수정하거나 삭제하지 않는다. 준비 중 본문이 바뀌었으면 최신 내용에 맞춰 수정한다.

관련된 기존 코드·커밋·검사·사진 링크는 유지한다. 틀리거나 사용할 수 없는 링크만 확인한 주소로 바꾸고, 별도 이유 없이 삭제하지 않는다. 같은 작업의 유효한 댓글은 갱신하며, 재시도나 형식 보완만으로 중복 댓글을 추가하지 않는다. 삭제 요청은 지정한 범위에서 처리한다. 이미 요청대로 정리되었으면 변경하지 않는다. 댓글 정리 결과를 설명하는 새 댓글은 만들지 않는다.

## 게시와 확인

- 게시 전에 사진·조작 시나리오·세부 결과·코드 링크를 포함한 본문을 완성한다. 이슈 게시 요청에는 해당 이슈를 설명하는 사진 첨부가 포함되지만, 별도 저장소·브랜치·릴리즈·외부 서비스 생성이나 임의 공개는 포함되지 않는다.
- GitHub 첨부 등 허용된 저장 위치에 사진을 업로드한다. 로컬 경로, 임시 미리보기, 업로드에 실패한 URL은 게시하지 않는다. 저장소 파일을 사용하려면 이미 게시된 파일인지, 해당 파일 게시가 요청 범위인지 확인한다.
- GitHub 첨부는 영구 `user-attachments/assets` URL을 본문에 사용하고, 미리보기·게시 본문에서 발급된 실제 이미지 주소로 표시와 접근을 확인한다. 영구 주소의 직접 GET 404만으로 업로드 실패를 단정하지 않으며 임시 서명 URL·JWT는 본문과 검사 기록에 저장하지 않는다.
- 이미지 업로드·접근·게시가 실패하면 상태를 먼저 조회한다. 같은 파일이나 댓글을 무조건 다시 올리지 않는다. 사용 가능한 업로드 방법이 없으면 게시용 자료를 완성한 상태로 두고 문제와 필요한 조치를 최종 응답에 명시한다. 사진을 빼거나 무관한 사진을 넣어 완료 댓글을 게시하지 않는다.
- 생성·수정 뒤 API로 대상 URL과 본문을 다시 읽고 코드 링크·사진 URL·본문이 의도대로 저장되었는지 확인한다. 이어 GitHub 페이지를 열어 이미지가 실제로 표시되는지 확인한다. API 성공만으로 이미지 표시까지 완료했다고 보고하지 않는다. 페이지 접근이 불가능하면 저장 여부와 이미지 표시 확인 여부를 구분하여 보고한다.
- 삭제 뒤 해당 댓글이 삭제되었는지 다시 조회한다. 응답이 불명확하면 상태부터 확인하고 같은 내용을 다시 게시하지 않는다.
- 간결한 문어체와 개조식을 사용한다. 뜻을 흐리는 표현, 전문적으로 보이기 위한 용어, 구어체를 제거한다. 사용자가 피하도록 지정한 표현은 적용하지 않는다. 실제 UI 라벨은 필요한 곳에 그대로 병기하여 화면에서 찾을 수 있게 한다.
- 최종 응답에는 게시·수정한 URL, 확인한 결과, 사용자 요청에 따른 문구·사진 검토 체크리스트를 적는다. 게시하지 못한 항목을 완료했다고 보고하지 않는다.
