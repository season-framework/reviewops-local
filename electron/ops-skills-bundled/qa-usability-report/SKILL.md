# QA 및 사용성 평가 보고서

이슈의 진행 상태, 실제 실행 결과, 사용자 불편을 구분하여 검사가 끝난 범위의 평가 보고서를 작성한다. 기본 산출물은 편집 가능한 HWPX와 같은 내용을 한글에서 내보낸 PDF이다. 사용자의 형식·도구·범위 지시가 이 기본값보다 우선한다.

## 검사와 기록

- 저장소·대상 앱·버전·실행 환경을 확인하고 이슈 본문과 댓글을 읽는다. 닫힌 이슈, 개발 완료 댓글, 자동 검사 통과만으로 UI 검사를 통과 처리하지 않는다.
- 이슈별로 고유한 QA ID, 검사 조건, 조작 순서, 예상 동작, 실제 결과, 판정을 연결한다. 서로 다른 시나리오를 합치거나 검사 재실행을 새 검사 개수로 중복 계산하지 않는다.
- 통과·오류 발견·기능 미제공·미실행·부분 확인을 사실에 맞게 사용한다. 제공하지 않는 기능을 실행 통과로 바꾸지 않는다. 접근 불가나 환경 부재를 기능 미제공으로 바꾸지 않는다.
- 소스 실행과 배포 앱, 시험 응답과 실제 AI 응답, 오류 주입과 운영체제의 실제 권한 거부를 구분한다. 모델의 전달 설정과 프로그램이 보고한 실제 사용값을 구분하고, 없는 사용값을 추정하지 않는다.
- 선택자 오류·대기 시간·잘못된 검사 예상값으로 실패한 자동 검사는 검사 도구 문제인지 먼저 조사한다. 제품 오류와 구분한 뒤 해당 조건을 다시 검사한다.
- 사용자가 컴퓨터 유즈를 지정한 조작은 UI에서 수행한다. 백엔드 값 변경으로 UI 검사 과정을 대신하지 않는다. 격리 자료 준비나 보고서 자동 생성도 사용자가 정한 도구 범위를 따른다.
- QA 요청만으로 제품 수정·릴리스·GitHub 게시까지 확대하지 않는다. GitHub 쓰기 작업은 별도 허용 범위 안에서만 수행한다. 해당 작업이 요청되면 사용 가능한 github-issue-management 지침과 연결한다.

버전 업데이트를 검사할 때에는 이전 버전·업데이트 경로·새 버전·데이터 유지·실패 처리·복구 결과를 각각 실제 수행한 조건으로 기록한다. 자동 검사, 패키지 확인, 실제 앱 조작은 서로 다른 검사이다.

## 전체 창 사진과 설명

- 프로그램 전체 창을 촬영하고 원본 파일을 보관한다. 중요 부분만 잘라낸 사진으로 대체하지 않는다. 원본에 번호·상자를 그려 저장하거나 내용을 생성·수정하지 않는다.
- 순서가 이어지는 화면은 같은 요청·자료에서 확보한다. 다른 실행 결과를 한 조작 흐름처럼 연결하지 않는다. 밝은/어두운 화면 등은 시험 조건 비교로 설명한다.
- 단계 제목, 전체 창 사진, 짧은 결과 설명을 배치한다. 사진 위에는 HWPX의 별도 도형으로 검정 테두리와 번호를 표시한다. 번호와 설명을 일치시킨다.
- 기본은 한 쪽에 사진 두 장이다. 가독성이나 표 분량에 따라 한 장을 사용한다. 세 장이면 첫 장을 결과표 아래에 두고 나머지 두 장을 다음 쪽에 둘 수 있다. 빈 공간을 의미 없는 사진·문장으로 채우지 않는다.
- 번호는 중요한 글자·버튼과 다른 번호를 가리지 않는 곳에 놓는다. 자동 위치 계산 뒤에도 한글에서 내보낸 PDF의 모든 사진을 직접 확인한다.
- 화면 표시 번호, 저장 순번, 스크롤 위치를 같은 것으로 단정하지 않는다. 화면에서 관찰한 범위만 설명한다.
- JPEG 바이트에 .png 확장자가 붙을 수 있다. 확장자가 아닌 실제 형식으로 삽입하고 원본 바이트와 비율을 유지한다.

## 문서 구성과 한국어

기본 순서는 표지·목차·종합 결과·검사 환경과 방법·이슈별 결과와 연속 화면·기능 제공 상태·사용성 평가이다. 필요한 항목만 사용하고 이슈 개수나 쪽 수를 고정하지 않는다.

- 본문·제목·표·테두리·머리말·쪽 번호는 흑백 또는 회색, 원본 화면은 컬러를 유지한다.
- 개조식의 간결한 문어체를 사용한다. 구어체, 과장, 꾸며낸 전문용어를 제거한다.
- 의미가 모호한 ‘축’, ‘근거’, ‘기준’, ‘n가지 ○○’, ‘현재 확인’을 문서용 장식 표현으로 사용하지 않는다. 실제 외부 문서 인용이 없는 ‘참고자료’ 항목은 만들지 않는다.
- ‘선행 실행’보다 ‘앞선 실행’처럼 직접 이해할 수 있는 말을 사용한다. 화면의 실제 버튼·문구 인용은 사실대로 유지한다.
- 사용성은 관찰한 문제와 사용자에게 생기는 불편을 함께 적는다. 기능 오류와 사용성 불편의 집계를 분리한다.
- 최종 보고서에는 다음 작업·남은 작업·개선 예정 목록을 넣지 않는다. 발견한 오류와 제공 상태를 완료된 평가 결과로 기록한다. 수행하지 못한 조건이나 한계를 숨겨 보고서를 완성한 것처럼 보이게 하지 않는다.
- 내부 JSON 파일 목록, 검사 도구 사용 기록, 문서 자체 점검을 제품 평가 본문에 넣지 않는다.

## HWPX 제작

보고서는 편집 가능한 HWPX와 동일한 내용의 PDF로 제작한다.

1. [입력 형식과 실행 방법](references/report-format.md)을 읽는다. [빈 입력 양식](assets/report-template.json)을 작업 폴더로 복사하고 실제 검사 결과·사진 경로로 작성한다.
2. 필요할 때 [두 화면 배치 예시](assets/layout-examples/page-19.png)와 [첨부 요청 흐름 예시](assets/layout-examples/page-36.png)를 본다. 두 파일은 과거 보고서의 **서식 예시**이며 새 검사 결과나 새 보고서의 사진으로 재사용하지 않는다.
3. scripts/build_report.py로 staging HWPX를 생성한다. 스크립트는 프로젝트·날짜·검사 개수를 정하지 않는다. 자동 쪽 수 추정과 도형 경고는 한글에서 출력한 결과를 확인하는 절차를 대신하지 않는다.
4. 한글 앱에서 열기·저장·PDF 내보내기를 수행한다. 원본이나 검토 중 파일을 덮어쓰지 않도록 작업별 파일을 사용한다. 사용자가 컴퓨터 유즈만 허용한 편집은 그 경로로 처리한다.
5. scripts/audit_report.py로 source JSON과 한글에서 저장한 HWPX의 본문·사진 바이트·실제 이미지 형식·회색 서식·QA ID·판정을 대조한다.
6. scripts/render_pdf.py로 최종 PDF의 모든 쪽을 렌더한다. 목차·제목·쪽 참조, 표 잘림, 사진 비율, 번호 가림·겹침, 설명과 사진 순서를 직접 검사한다. 수정 후에는 바뀐 쪽을 재검사하고 나머지 쪽은 렌더 이미지 해시로 동일성을 확인할 수 있다.

한글에서 저장하거나 PDF를 확인하는 작업을 수행하지 못했으면 그 상태를 정확히 말한다. 파일 생성이나 XML 검증만으로 완성된 서식이라고 선언하지 않는다.

## 전달 전 점검

- 이슈·QA ID·판정 집계 일치, 재실행 중복 계산 없음
- 실제 조작·시험 조건·미제공·미실행 구분
- 전체 창 원본·번호·단계 설명 일치
- 표·본문 누락 없음, 목차·쪽 참조 일치
- 흑백 서식·원본 사진 유지, 전쪽 시각검토 완료
- 구어체·모호한 용어·불필요한 다음 작업 목록 없음

최종 응답에는 산출물 링크와 핵심 결과를 적고, 위 점검에서 실제 완료한 항목을 짧은 체크리스트로 제공한다.
