# Shared-data query boundary

`querySharedData(snapshot, callerContext, operation, payload)` is a synchronous, transport-free query kernel. It has no Store, Electron, filesystem, network, or credential dependency. The local main-frame adapter described below connects this kernel to trusted local IPC. No remote or device transport is connected.

The application must obtain one immutable Store snapshot and construct the caller context itself. The context is `{projectGrants: [{projectId, read: true}]}`; an empty list permits nothing. Missing, malformed, broadened, or duplicate grants are rejected. Contexts and grants are exact data objects. The operation payload cannot supply grants, identity, roles, or extra options. This separation is an application contract, not proof of device authentication.

| Operation | Exact payload | Response |
| --- | --- | --- |
| `projects.list` | `{}` | `{version: 1, projects}` containing only granted projects still present |
| `reviews.list` | `{projectId}` | `{version: 1, projectId, reviews}` |
| `reviews.get` | `{projectId, reviewId}` | `{version: 1, projectId, review}` |
| `comments.list` | `{projectId, reviewId}` | `{version: 1, projectId, reviewId, comments}` |
| `attachments.list` | `{projectId, reviewId}` | `{version: 1, projectId, reviewId, attachments}` for direct review attachments |

Every review lookup first requires a grant for the explicit project and confirms that project exists. A review is resolved only within that project. Missing, unshared, and wrong-project resources produce the same `NOT_FOUND` code and fixed message. Unknown operations and unsupported payload fields produce `INVALID_QUERY`; malformed grant contexts produce `ACCESS_DENIED`. Invalid selected stored values or ambiguous duplicate rows produce the fixed `INVALID_SNAPSHOT` error, with no input values attached.

A project contains only `id`, `name`, `description`, `createdAt`, and `updatedAt`. A review contains only `id`, `projectId`, `number`, `title`, `body`, `status`, `priority`, `category`, `createdAt`, and `updatedAt`. All records, arrays and envelopes are newly constructed. No nested source object is returned or mutated. Stored private fields are not traversed. Status/priority choices, text lengths, ID grammar, timestamp format, and the positive integer number follow the current Store's field types. Custom category IDs are retained. The 100,000-row bound follows the existing Store import bound; this is not a network response-size guarantee.

Titles, bodies and descriptions are deliberately shared user content and are preserved. This module is not a secret scanner for free-form content. Structured connections, settings, paths, URLs, evidence, logs, agent material and attachment bytes/storage paths are omitted. Only the user comments described below are projected from activities. The direct review-attachment metadata projection is described separately below; other activity history, run status and all comment-linked attachments remain omitted.

## User comments

`comments.list` returns only activities with `type: 'comment'`, `role: 'user'` and an empty `agentRunId`. A user-role row linked to an agent run is an agent prompt and is omitted, along with agent responses, system rows and created/updated/status events. Each comment contains exactly `id`, `reviewId`, `body`, `createdAt` and `updatedAt`; it makes no author-identity claim. The existing pre-v3 SQLite migration and logical import supply explicit user-role/empty-run fields for old comments. The query requires the current fields and never treats a missing role as user or accepts raw backup rows as a normalized snapshot.

An empty body is valid, including an attachment-only comment. The query neither reads the omitted attachment/evidence fields nor invents replacement text. A selected body must already be a string of at most 100,000 JavaScript UTF-16 code units without NUL. Its exact text, whitespace, Unicode and line breaks are preserved without trimming, coercion, redaction or truncation. IDs and timestamps use the existing query validators. Invalid classification, duplicate activity IDs within the requested review or malformed projected fields fail with the fixed `INVALID_SNAPSHOT` error. Bodies and other private fields of excluded rows are not evaluated.

The result preserves the supplied snapshot order. Production Store snapshots order activities by `createdAt`, then SQLite `rowid`, so equal-time insertion order is retained without exposing `rowid`. This is not a durable change cursor. The new call permits at most 1,000 eligible comments and 4,194,304 bytes for its complete UTF-8 JSON success envelope, including escaping, fields and separators. The 1,001st eligible row is rejected before its body or timestamps are read. Either limit returns `QUERY_LIMIT_EXCEEDED` with the fixed message `Shared comments exceed the local query limit.`; no partial list or fabricated empty success is returned. These are local-query limits, not a network framing or pagination contract.

Project/review authorization precedes access to activities. The existing three operations keep their exact version-1 DTOs and error behavior and do not require or inspect activities. The new success envelope also uses `version: 1`; no Store schema, backup, ordinary snapshot, preload, MCP or connection-info version changes.

The caller must not independently fetch portions of a snapshot across awaits. A future adapter must re-resolve grants on each operation and must not trust a peer's context. Network pagination/byte limits, device authentication, revocation sessions, durable revisions, command receipts, restore epochs and transports are future work. No placeholder revision or epoch is emitted here. No mutation, listener, relay, remote UI, or #10/#11 completion is provided.

Focused tests use only synthetic in-memory objects and Node's built-in test/assert modules. They cover exact DTOs, foreign/missing IDs, strict payloads/grants, private-field omission, detached results, frozen input, malformed selected fields, duplicate rows, custom categories, and grant revocation. On canonical base `4651b5b0bbee0603fd1a8e6edeba8a7b78f28bf0`, all 15 focused synthetic contracts passed once with Node v24.22.2; none failed or skipped. No app, transport, or existing adapter was exercised.

## Direct review-attachment metadata

`attachments.list` projects only attachments whose `reviewId` is the authorized selected review and whose own `activityId` data property is exactly `null`. Every non-null link must be a syntactically valid stored activity ID and is excluded. This first slice omits attachments on ordinary user comments, run-linked user prompts, agent responses and system/history rows alike; it does not inspect activities or infer their classification. Missing, accessor-valued, empty-string or malformed activity links are not treated as review-level ownership.

Each result contains exactly `id`, `reviewId`, `name`, `mimeType`, `size`, `sha256`, `createdAt` and `updatedAt`. Names are nonblank strings of at most 255 UTF-16 units, without NUL, slash or backslash, and cannot equal `.` or `..`. MIME values follow the Store's nonblank 255-unit text constraint; they are declared metadata, not verification of a file's content type. Size is an integer from zero through 1,073,741,824. Digests are exactly 64 hexadecimal characters, and their original case is preserved. IDs and dates follow the existing stored validators. Values are preserved without coercion, normalization or secret scanning. The Store normalizes new/imported names and MIME strings before storage; this reader does not repair stored rows.

Project/review authorization precedes reading `snapshot.attachments`. For a foreign review row, only its review ID is inspected. Within the selected review, IDs and activity links are classified before metadata projection. Duplicate attachment IDs within that review fail with `INVALID_SNAPSHOT`, including on excluded linked rows. Storage names, local paths, URLs, file bytes, nested evidence and activity bodies are never read. The supplied snapshot order is retained; production Store snapshots order attachments by `createdAt`, then `id`. All arrays/records are detached and no filesystem operation occurs.

At most 1,000 eligible rows and 524,288 bytes are permitted for the complete UTF-8 JSON success envelope, including escaping, field names, outer IDs and separators. The 1,001st eligible row is rejected before its name, MIME, size, digest or dates are evaluated. Either limit returns `ATTACHMENT_QUERY_LIMIT_EXCEEDED` with the fixed message `Shared review attachments exceed the local query limit.` No partial result is returned. The existing comment limit code/message and all four earlier operation contracts remain unchanged. These limits describe a local query, not a network protocol or pagination cursor.

## Local main-frame adapter

The local IPC actions `shared.projects.list`, `shared.reviews.list`, `shared.reviews.get`, `shared.comments.list` and `shared.attachments.list` map to the kernel operations with the same exact payloads. They use the existing request/invoke envelope; there is no new preload capability or external integration action. Existing renderer snapshots and automation/MCP response contracts are unchanged. The comment and direct review-attachment queries do not write Store data, advance revisions or receipts, emit data-change notices, create or focus windows, or start agent operations.

The main process queues each read behind prior application mutations. At execution it revalidates the original trusted main-frame sender and owned window record, then captures one current Store snapshot and calls the synchronous adapter without an intervening await. A closed or replaced sender is refused; the focused window is never adopted.

Only an explicit empty server record project ID denotes the unbound main window, which can read projects in that snapshot. A project window can read only its server-owned project ID, including after QA release. A deleted bound project returns no projects and cannot broaden to other projects. This is the policy of the new shared queries; existing ordinary project-window navigation is not represented as a general backend authorization boundary. Renderer tabs, stale dirty drafts, URL parameters and payload grants do not determine this scope.

With Node v24.22.2, two scoped commands each passed once: 23 kernel/adapter contracts and eight selected actual main-handler contracts, with no failures or skips. The 15 kernel contracts repeat the earlier milestone; the eight adapter and eight handler cases are new. The handler checks use mocked Electron windows with a production Store/Vault in owned temporary files. The remaining main-handler suite was not executed. No renderer build, actual app/frame/OS interaction, network, remote permission, revision, command receipt or restore epoch validation is established by these synthetic checks.

Those recorded results belong to the original three-operation milestone; they do not record validation of `comments.list`.

Two subsequent focused commands passed 31 kernel/adapter tests and 12 selected main-handler/legacy Store tests (43 passes, zero failures or skips). This total includes 12 new comment-query cases and 31 earlier contracts. The checks used source code, mocked Electron windows and owned temporary SQLite databases; they do not establish behavior in an actual app, across a network, or between two PCs.
