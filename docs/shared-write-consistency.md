# Durable review-write consistency core

This milestone adds an internal Store boundary, not a renderer, IPC, MCP, remote-write or cross-PC feature. Existing local writes are not conditional yet. Do not expose the new status command until local editors and every asynchronous writer carry admission epochs and deliberate revision tokens through their eventual commits.

## Persistence and compatibility

Database schema 11 adds `dataset_meta`, `review_revisions` and `command_receipts`. They stay outside business snapshots, `TABLES` and logical exports. Logical backup format remains 10, and imports still accept formats 1 through 10. Unsupported top-level backup fields, including control metadata, are rejected. A physical SQLite/profile copy contains control data; this in-database epoch does not detect rollback of itself.

The unpredictable dataset epoch persists across restart. A successful logical import rotates it, retires old receipts and reseeds revisions in the same live transaction as business replacement. Independent validation epochs are never imported. Failed validation or live replacement preserves the original business graph, epoch, revisions and receipts. Old exhausted counters are reseeded only inside that rollback-capable epoch transition.

## Aggregate and writer coverage

A revision is an opaque monotonic invalidation token, not a count of user actions. Database triggers cover insert, update and delete on reviews, activities, attachment metadata, agent runs and saved follow-up requests. Child owner moves invalidate both reviews. Direct queue SQL, agent progress, completion/transfer, startup interruption, review copy/version/target edits and service-link/FK changes therefore use the same boundary. File contents, project headers, settings, runtime readiness and process ownership are outside this aggregate.

A review deletion marks its sidecar as a tombstone before cascade work. Child triggers increment the existing sidecar without reviving it. Reusing a review ID increments its retained counter and records that birth revision in an internal `generation` field. A receipt committed before that birth cannot be replayed against the new row, while ordinary later edits still allow the original receipt. The public token remains epoch plus revision. Values are constrained to safe positive JSON integers. Overflow or a missing sidecar aborts the business statement. No exact per-action increment is promised.

## Synchronous internal command

`reviewWriteState({projectId, reviewId}, callerProvider)` reads a scoped status, epoch and revision in one Store transaction. `setReviewStatusCommand(intent, callerProvider)` accepts exactly `requestId`, `projectId`, `reviewId`, `epoch`, `expectedRevision` and `status`. Both APIs require a synchronous application-owned provider returning `{principalId, projectGrants: [{projectId, write: true}]}`. This is an internal authority input, not a payload, device authentication system or persisted pairing record.

The command obtains current grants inside `BEGIN IMMEDIATE`, scopes the actual review and checks the live epoch before looking up a receipt. Missing and unauthorized targets share fixed `NOT_FOUND`. An identical original intent returns the immutable original acknowledgement before comparing the now-current revision; changed intent with that identity conflicts. Revocation and deleted/no-longer-owned targets are checked again even for retries. A new intent compares the revision, checks the 100,000 active-receipt budget, applies normal Store status/activity rules and inserts its bounded acknowledgement atomically. A no-op status stores a receipt without changing the aggregate revision. Receipts cannot be updated or deleted in their active epoch; no active identity is silently evicted.

The fingerprint is SHA-256 of a versioned fixed primitive tuple. Acknowledgements contain only operation/target/identity/status, committed epoch/revision/time and a changed flag, with a 4 KiB bound. Notifications remain a future after-commit responsibility. Promise/thenable transaction results are rejected, and a caught nested transaction failure still forces outer rollback.

## Original local dispatch admission

`captureWriteAdmission()` creates an opaque, frozen, process-local capability bound to one Store instance and its current dataset epoch. `assertWriteAdmission(admission)` checks that original ownership and epoch in a short synchronous transaction. Neither operation changes business data or receipts, exposes the epoch, nor grants project access. A serialized copy, caller-created object or capability from another Store is invalid. A committed logical import makes an earlier capability stale even when the imported project and review IDs are identical; a rolled-back import leaves the original capability usable.

Main captures this capability before a Store-persisting dispatch waits on `actionQueue`. An explicit action inventory covers group/project/service/review changes, review categories and versions, activity add/update, settings, attachment add/delete, persisted agent start/cancel/transfer and request changes, SSH trust, and logical import. It is separate from `changesData`, which remains only the existing notification matcher. On local IPC execution, main rechecks the original main-frame sender, window-record identity and project/QA scope before asserting admission and entering dispatch. A renderer payload cannot supply or upgrade this capability. Reads keep their current behavior and can observe a completed restore.

This is an entry fence, not an atomic wrapper around asynchronous dispatch. No SQLite transaction is held across an `await`. At that milestone, delayed agent callbacks, request start completion, attachment staging, version/copy reads and file cleanup still needed original admission through their eventual commits. Existing integration dispatch captures one capability per dispatch; an automation action spanning several awaited dispatches is not fenced as one original action yet. It must not be described as fully restore-safe. This slice adds no renderer edit revision, command adapter, grant provider, status IPC/MCP command, authentication or transport. The internal status command remains unexposed until those later fences and local reconciliation are complete.

## Original agent and saved-request ownership

The next source-only slice carries an immutable, main-created operation frame explicitly from the original dispatch through agent attachment reads and runtime preflight. There is no payload epoch, current-context fallback or replacement admission after a wait. Before its first material or preflight await, the launch captures an opaque original review-incarnation admission. The launch transaction asserts the original epoch, review generation and originating window/project/QA scope before saving the run and its user activity. The existing active-work refusals during backup restore remain in place; controlled Store-import tests do not relax those UI rules.

Each original agent job retains its own application callback closure inside its manager. That closure captures the original admission, manager cohort and review/project/service membership. These process-local owners are absent from public job data, Store records and backups. Callback persistence checks the original epoch, review generation, accepted run identity and current membership in the same synchronous Store transaction as progress, response and activity writes. Its in-memory update and notification use the actual row returned by Store, including a terminal row that wins against conflicting incoming progress. A durable terminal status does not release the original manager owner: busy checks, workspace conflicts, cancellation and active counts retain that owner until the original manager sends its final notification. This is not proof of physical process or stdio closure; the existing manager still owns those resources. A stale callback can finish its original resource cleanup but cannot write into a restored graph, adopt a new owner with the same ID, or remove that owner's job or unique operation token.

Running jobs keep the existing policy that closing their original window does not cancel them or discard their legitimate progress. Their already accepted callback owner uses its original epoch and current target membership, rather than requiring that old window to stay open. A launch still waiting on preflight must pass the original window/scope check before it can start. Startup reconnection gets a newly admitted manager/job owner. After a successful logical import, interruption of imported runs is an explicitly new-epoch maintenance transaction; old callbacks are never upgraded to that admission. Failed or cancelled imports retain their original epoch behavior.

Saved-request starts retain an original admission, review-incarnation token, execution-content identity and an exact pending-owner object before scheduling work. Before invoking the original start callback, the queue checks the current request and readiness without holding a transaction across the asynchronous start. Completion re-reads the row and asserts the original epoch, review generation, pending owner, execution contents and review/project identity in the same transaction as the run link. The content identity includes original creation time/signature and submitted prompt, prerequisites, target, settings and context. It excludes unrelated result notes/resolution and update timestamps, so those current fields are preserved instead of overwritten by a captured-row UPSERT. A stale pending promise cannot join or delete a newer same-ID owner, recreate a removed request, or overwrite restored request contents. Same-epoch retries can still share their one admitted start; failed imports leave that owner usable.

The private attachment helper accepts a synchronous committed continuation for this agent-launch call only. It runs after the existing DB/file rollback catch and before the helper yields its successful Promise. The original accepted owner is therefore registered and the manager starts in that same call stack; a window-close microtask sees an already accepted running job, rather than a committed ownerless record. Synchronous scope loss during recording instead transitions only the accepted original run to failed after rechecking its epoch, incarnation, membership and exact owner, and preserves the caller's original rejection. Stale targets are never rewritten. Unexpected failure to persist that cleanup holds the original owner/operation as unconfirmed rather than reporting completion. Initial DB/attachment rollback never registers a launch owner. Other attachment callers have no committed continuation and keep their existing behavior. This is not a general attachment/file fence.

`captureReviewWriteAdmission(admission, {reviewId, projectId, serviceId})` and `assertReviewWriteAdmission(token)` are internal Store/kernel helpers. The token is immutable, fieldless, process-local and Store-bound; its private record retains the original admission and the existing `review_revisions.generation`. Ordinary revision changes keep it valid. A Store/SQL delete-and-reinsert that runs the existing review-birth trigger invalidates it even when all public IDs match. No generation/epoch/grant is accepted from a payload or added to schema, exports or backups. Arbitrary direct SQL that restores identical execution contents and timestamps or rewrites control tables is not a supported row-incarnation protocol.

## Original selected-material version saves

The existing `review.version.save` dispatch now passes its original main-owned operation into the version helper. Before its first asynchronous attachment read, one synchronous Store transaction captures the review, version state, every selected attachment metadata row and an opaque snapshot admission. That admission reuses the original epoch and review-incarnation ownership and additionally retains the original aggregate revision. It is process-local and Store-bound; no payload can provide or renew it. Ordinary agent callback admission deliberately remains revision-independent.

After each original byte read, and again in the same synchronous transaction as the final version write, the helper checks the original window/QA scope, epoch, review incarnation and revision, and the exact selected attachment membership and metadata. No SQLite transaction spans an await. A successful same-ID logical import, review replacement, aggregate edit or selected-row change refuses the old save. A rolled-back or invalid import leaves the original operation usable. This is deliberately conservative: a legitimate same-review history update also requires the user to recheck before saving the selected version.

An epoch, incarnation or revision refusal keeps its structured cause and shows a localized request to recheck the copies. Invalid frames and unrelated integrity errors retain their own error. Rejection sends no data-change notification or success response. The existing renderer caller returns null on rejection, retains its target/source/selection and does not show a success toast. Controlled tests execute that actual caller code without launching a UI; they are not native-app observations. The version-list reader, copy path, general attachment staging/rollback, persisted renderer edit bases and multi-dispatch automation remain separate boundaries. No schema, backup format, IPC payload, public conditional writer or remote transport is added.

## Original direct attachment additions

The existing `attachment.add` operation captures its original main-owned frame and an opaque Store-bound attachment admission before the file picker or file reads. This separate private capability retains the original dataset epoch, review birth and project. It has no service binding or expected aggregate revision: a legitimate agent-history update, next-service selection or project-service link change does not invalidate an attachment that still belongs to the original review. Agent and version-snapshot tokens cannot be substituted for this capability, and it grants no payload-supplied authority.

After preparation, the operation checks the original frame and admission before writing physical attachment files. The same checks run inside the existing final attachment-save transaction before its rows are inserted. No SQLite transaction spans the picker or file-read awaits. The original primitive review and optional activity IDs are retained; the activity must still belong to that review. This does not establish a separate activity-incarnation protocol for arbitrary same-ID raw SQL replacement.

Local IPC frames also retain a private per-window QA-scope incarnation. A real activation change replaces that process-local identity, so release followed by reopening the same project in the same window cannot renew an older request. Repeating an unchanged activation or changing another window leaves its identity intact. This adds no payload field, grant or persisted revision and does not tighten already accepted agent callbacks. The attachment target checks the current original project and review birth; it does not record an unchanged-generation project's entire move history, including a controlled A-to-B-to-A sequence.

Only this attachment-add path maps stale epoch and review-birth/project refusals to localized guidance to select the files again, retaining the structured code and original cause. Existing scope, window and unrelated file-integrity errors keep their own messages. It does not promise to retain a completed picker selection after refusal.

The pre-change controlled main test held the mocked picker boundary, released the actual QA session through its normal handler and then completed selection. The old operation returned success when the test required refusal. This is a genuine main/Store test counterexample, not an actual Electron dialog or GUI reproduction. The focused regressions cover that scope loss, replaced main frames, imported epochs, moved or recreated reviews, accepted agent history, service-independent attachment membership, retained targets and rollback of a failed attachment commit. Review replacement and import schedules use controlled Store seams; normal queued UI operations are not claimed to interleave that way.

This boundary applies only to direct `attachment.add`. General staging tokens, screenshots, copy preparation, other attachment-save callers, deletion staging and file rollback remain separate work. Existing rollback is not promoted to joint filesystem/SQLite crash atomicity. No schema, backup, renderer edit token, IPC payload or remote writer is added.

## Original run ownership and the next selected service

An accepted agent run retains its original review generation, project and execution identity when the review's next selected service changes. Its callback may save only that original run and its history while the original service remains linked to the original project. It does not overwrite the current service selection or reviewer notes. Appending legitimate agent history still updates the review's modification timestamp through the existing Store rule.

`assertRunningReviewCallback(token)` checks the opaque original Store admission, epoch, review generation, project and non-null original service link inside the callback's persistence transaction. Main also checks the original manager cohort, exact job owner and run execution tuple. Restored epochs, moved or recreated reviews, removed original links and replaced owners or executions remain invalid. This assertion does not grant a new launch, accept a payload flag, expose a public command or replace strict launch and saved-request admission.

Explicit service-deletion maintenance has a different link condition: the original service must already be unlinked. The current selection may be null or a different service that is still linked to the same original project. The original deletion scope, epoch, review generation, manager, owner, execution, settled cancel promise and observed final event remain required. The original run’s final state is saved and only its active ownership is released; another accepted run for the current selection retains its callback and active-work ownership. Normal callbacks still cannot persist after their original service is unlinked.

The regressions retain QA-06's same-folder, identical-input scenario: a retry waits on attachment reading while another accepted run adds its completion history, and ambiguous fixture source selection remains rejected. Other contracts cover current selection and notes preservation, the existing history timestamp rule, an independently running next-service owner, forged or service-free tokens, stale epochs, moved or recreated reviews, replaced executions and dangling next selections. The held retry is observed immediately and released and awaited in an inline `finally` before database teardown; simultaneous assertion and pending-launch errors are both retained. File operations, renderer revisions, remote activation and native or packaged validation remain separate boundaries.
