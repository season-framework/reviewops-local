# Development service observation and managed local Node services

This change implements one local execution path for issue #15. The cause of the earlier connection failure remains unknown because logs from that time are unavailable. SSH services, general shell commands, process-tree management, persistence across host reboots, and adoption of existing processes are outside this implementation. Do not mark the entire issue complete on the basis of this scope.

## Usage

After packaging, the installed bundle copies the original bootstrap from ASAR to `resources/owned-services/owned-node-bootstrap.cjs`. The standalone Node process receives this real file path, and the command in its startup response is checked against the same path. Source runs use the bootstrap in the repository. The main process selects this path internally; user execution settings and external tool requests cannot change it. Keep this packaging check separate from actual UI verification in the installed app.

Expand **Service readiness** (`서비스 준비 상태`) in the project's review-target screen. Observation checks send an unauthenticated GET from the ReviewOps computer. A 2xx response header does not prove that the actual save/use flow succeeds or describe the internal state of an SSH host. Redirects are not followed, and response bodies are not stored. The hash of a selected comparison file is not evidence of the file that is actually executing. Observation results are temporary screen state.

Local connections show **Managed local Node service** (`관리형 로컬 Node 서비스`). In the main project screen, save the absolute path to a separately installed Node executable, a relative `.cjs` entry file within the working directory, arguments as a JSON array of strings, and a loopback HTTP readiness URL. **Start saved service** (`저장한 서비스 시작`) creates a child process owned by the main process. Saving the configuration or relaunching the app does not start the service automatically. The initial supported scope excludes the Electron executable, npm/shell wrappers, and ESM entry files. Do not put secrets in arguments. Configuration and arguments are stored in `owned-node-services.json` in the user data directory with mode 0600 and discarded during backup restoration. The total serialized configuration is limited to 1 MiB. If an additional save exceeds this budget, it is rejected before writing the file or replacing the current configuration, so the next app launch can still use the existing configuration. These settings are excluded from backup exports.

**Check saved readiness URL** (`저장한 준비 URL 검사`) is a separate HTTP observation. `running` means the owned Node process has sent its IPC startup response; it does not mean the service is ready. The UI states that URL ownership is unverified. An external server returning 200 at that URL, or a Node service ignoring EADDRINUSE, does not associate the external response with the owned service. Actual `net.Server` listen addresses reported by the child are shown as a separate source and are not treated as proof of HTTP response ownership. The actual core button, POST, and saved values require separate checks.

Configuration drafts participate in the project's unsaved-content state. When the connection or working directory changes, runtime state and observations switch to the new connection, while the draft being edited and its original project/connection information are retained. The draft remains visible for SSH connections and when no connection is selected. Users can return to the original connection and continue editing, or explicitly discard it. For a new local connection in the same project, users must select **Review in this connection** (`이 연결에서 검토`), pass file checks against the current working directory, and save before starting the service. The draft is not saved to another project or executed automatically. If the connection changes while a save is pending, the earlier save response does not mark the new draft as saved.

## Execution information and lifecycle

- The main process retains `projectId + connectionId + instanceId` and the exact ChildProcess/IPC channel. The actual Node executable, startup argv, application argv, cwd, PID, Node version, and report time are collected through that child's channel. The start time and random instance ID are execution records maintained by the main process. This ID is neither an HTTP nonce nor independent OS attestation.
- The executable and entry SHA-256 values are **prelaunch file snapshots**. File type, identity, path, size, and modification time are checked through open file descriptors, and files are read in bounded blocks. A file may change before loading, so `loadedBytesVerified:false` applies and the result is not described as `attested-loaded`. Comparing the running process's `process.execPath` with the actual spawn target does not verify every loaded code byte.
- Services do not belong to an agent job/process group or renderer. Closing a project screen or completing/canceling an agent does not send a stop command to the service. Reopening the screen reads the main-process state. At this stage, start/stop is available only through the trusted app renderer; external MCP/API clients and embedded web pages receive no execution or control access.
- **Stop/recover this instance** (`이 인스턴스 중지/복구`) requests cooperative shutdown through the retained child IPC channel. The bootstrap calls close on the actual tracked servers to stop accepting new connections and waits for accepted requests. In-flight HTTP requests are not interrupted; subsequent new HTTP requests on a connection that remains writable are rejected with 503/Connection: close. For the plain HTTP scope below, shutdown also routes `checkContinue` and `checkExpectation` through this refusal policy before Node can write an automatic 100 or 417 response. Default and custom Expect handling before shutdown, including bodies already accepted by a custom handler, retain their normal behavior. Idle keep-alive connections are closed after requests finish. The bootstrap does not use `closeAllConnections` or interrupt an accepted request’s socket.
- A plain `http.Server` can also have an unused TCP preconnection with no HTTP request. After requesting server closure, the bootstrap sends a graceful FIN only when that connection has no accepted request and zero bytes read, written, or buffered. Once its write side finishes, the same conditions are checked again before the standard `socket.destroySoon()` releases that unused connection, so a peer that keeps its write side open does not retain this resource indefinitely. This handling requires the exact `http.Server.prototype`; raw TCP/TLS servers, HTTPS servers, and subclasses are excluded. A partial header or accepted request keeps its existing drain behavior. A peer attempting its first HTTP request, upgrade, or CONNECT after FIN can encounter the closed transport; that input was never accepted by the entry. If input is observed before the resource-close check, the connection is kept on the existing refused-input drain path. No response or entry delivery is attempted on an already-FIN connection. Accepted requests, partial headers and other referenced work can still leave shutdown unconfirmed.
- During initial loading, the entry may optionally export `exports.reviewopsShutdown = async ({reason}) => { ... }`. `reason` is `stop` or `parent-disconnect`. The hook is called once per instance and awaited in parallel with server closure. Use it to clear the entry's own intervals and wait for separate work/writes to finish. A referenced bootstrap handle keeps the process alive even when only an unresolved Promise remains. Hook rejection or noncompletion is not treated as completion.
- Once every listener has closed and the hook has finished, the bootstrap sends a private completion marker to the parent. After receiving an acknowledgment for the same instance, it releases only its own IPC and keepalive. The successful path does not call `process.exit`. Referenced requests, timers, and file I/O must finish naturally before the child exits. The parent permits completion and a new instance only after observing both the marker and the exact child's actual exit code 0 with no signal. Exit 0 without the marker does not count as completion of the requested shutdown. This contract does not guarantee completion when an entry deliberately calls `process.exit`, for unref'ed work, or for arbitrary descendant processes.
- There is no PID input, signaling of reused PIDs, inferred port ownership, process-name search, killall, or forced-termination fallback. If cleanup or natural exit is not confirmed within the deadline, the state remains `stop-unconfirmed`, and new starts, recovery, and successful app shutdown are rejected. Cleanup of a live child continues; later observation of the marker and actual exit updates the state.
- Normal app shutdown first confirms cleanup markers and exits for owned services, then closes each window. The discard-unsaved-content prompt appears once in response to that window's actual renderer unload veto. A previously inspected dirty value or consent in another window does not authorize closing it automatically. Input entered while cleanup is pending, or new input after earlier consent, is handled again during that window's final close. Electron's close() return is not considered completion; the actual closed event for the same window is required. Time spent answering the discard prompt is excluded from the window-close deadline. After the response, the remaining close time for that same shutdown attempt resumes. An explicit close veto, a new window, or failure to close within 10 seconds cancels only that shutdown attempt. Canceling to continue editing may leave services already stopped. Stopped services do not restart automatically. Remaining windows and drafts are retained, but windows already closed after consent to discard are not restored. This differs from the previous approach of checking every window in advance.
- Parent IPC disconnection also attempts the same listener/hook cleanup and natural exit, but this handling is not guaranteed during an event-loop stall, forced process termination, or app crash. A new app instance neither adopts nor cleans up historical PIDs. Entries that create arbitrary descendant processes are unsupported, and termination of those descendants is not guaranteed. No OS-wide autostart is installed.
- While an owned service is running, changes to its project connection, connection deletion, project deletion, group deletion, and backup restoration are rejected. Work in other projects can continue. Every asynchronous operation checks connection generation and the app-shutdown lifecycle so that A→B→A changes or a late start after shutdown cannot overwrite newer state.

## Verification scope

Unit checks and actual Node child fixtures in private temporary directories/on loopback cover HTTP POST persistence, actual child information/listen observations, selected-instance stop and recovery with a new identity, preservation of external ports, EADDRINUSE plus external HTTP 200, unconfirmed shutdown, races, and file-replacement boundaries. Targeted plain-HTTP fixtures also cover graceful write completion and resource closure for an unused half-open preconnection, preservation of partial headers, accepted POST and later asynchronous writes, a first request, upgrade, CONNECT, or Expect request arriving after FIN, accepted custom Expect POST bodies and later writes, unchanged default Expect behavior before shutdown, writable draining Expect refusal, raw TCP/TLS exclusions, and re-listening without duplicate connection observers. The main-process unit harness checks actual storage/permission boundaries, while Electron windows are mocked. These fixtures do not establish product UI behavior, actual agent CLI lifetimes, installed-app or native Windows/ARM behavior, SSH behavior, or app/host restart behavior. See the [separate real packaged demonstrations and their recorded limits](https://github.com/season-framework/reviewops-local/issues/15#issuecomment-6560333386) for evidence outside this fixture scope. The existing PR39 Mac synthetic investigation with 4 conditions × 4 checkpoints is separate historical evidence and is not counted as new product QA.

Node API references: [ChildProcess IPC and exit](https://nodejs.org/docs/latest-v24.x/api/child_process.html#event-exit), [process.disconnect](https://nodejs.org/docs/latest-v24.x/api/process.html#event-disconnect), [process.exit](https://nodejs.org/docs/latest-v24.x/api/process.html#processexitcode). Successful IPC delivery and actual process exit are distinct events.
