# Ops session transport

`electron/ops-session.cjs` owns one connection and one persistent Codex thread per goal. `ops-manager.cjs` owns durable goal state, target claims, prompt assembly, delivery records and schedule changes. A healthy connection is reused for both new turns and steering. A runtime selection change takes effect when a connection is reopened, without replacing the saved thread.

The integration uses the [official app-server protocol](https://learn.chatgpt.com/docs/app-server) and was checked against schemas generated by the installed `codex-cli 0.166.0-alpha.5.1` with `codex app-server generate-ts --experimental`. Experimental API support is requested during initialization.

## CLI compatibility

Ops requires the validated protocol baseline **Codex CLI 0.166.0-alpha.5.1 or later**. This is the version against which ReviewOps verified its experimental history, dynamic tools, image outputs and background-terminal lifecycle; it is not a claim about the earliest upstream version introducing those features. Prerelease identifiers are compared using SemVer ordering without a development-only dependency.

The selected local runtime's validated version is checked before thread allocation. A runtime supplied without a version is queried with a bounded `--version` call. SSH checks the selected executable's version on the same verified connection, with the same directory and PATH, before starting app-server. Unsupported versions give a goal-specific instruction to update the selected CLI; they do not create a replacement goal conversation.

Before first model input on a connection, Ops probes the paginated history method and background-terminal listing. The validated CLI reports an idle, unmaterialized empty history with `-32600`; an unknown method or malformed response is rejected. A newly allocated thread is persisted before these checks. Only that known-empty thread receives a cleanup capability probe. Resumed owners are never cleaned for compatibility testing. Dynamic tool registration and the validated baseline establish the image-response contract. A failed pre-input probe is recorded as `not_sent`, retains any already allocated empty thread ID, and permits no silent downgrade or new-thread retry.

## Execution and history

The goal's selected model, reasoning effort, sandbox and approval settings are applied to its thread. The adapter defaults to `workspace-write` and `never`; it does not inherit this development chat's permission level. Unsupported settings fail before input delivery. Approval or user-input requests without a wired product handler are refused and reported as `OPS_APPROVAL_REQUIRED`.

The thread ID is reported to the manager and its persistence callback is awaited before submitting a first turn. Fresh empty threads expose idle metadata before their first turn has materialized history. A newly admitted input can start from that idle metadata; recovering an ambiguous input still requires actual history.

| Observed state | Operation |
| --- | --- |
| No allocated thread | `thread/start`, then `turn/start` |
| Saved thread after connection restart | `thread/resume` using the original ID |
| Idle thread | `turn/start` on that thread |
| Active turn | `turn/steer` with its `expectedTurnId` |
| Pause or finish | `turn/interrupt` when active, confirm terminal turn history, then clean and verify this thread's background terminals |

A successful interrupt acknowledgement alone is insufficient. Completion notifications and subsequent thread history distinguish `completed`, `failed` and `interrupted`. Shell commands that yielded into a background session can survive a turn interrupt. Pause and finish therefore also call `thread/backgroundTerminals/clean` for the bound thread and paginate `thread/backgroundTerminals/list` until no terminal remains. This applies to an idle saved thread too. Unsupported cleanup, a lost response, malformed pagination or still-running terminals leave cleanup unconfirmed; the adapter never falls back to an operating-system process kill. A late start response cannot change an already observed completed turn back to running.

Model turn state and background ownership are separate. A normal completion probes the bound thread's terminals before publishing its terminal event. Completion events and idle reconciliation/delivery results carry `backgroundState: "active" | "empty" | "unknown"` and a count only when established by all pages. An idle model with a running service still owns its target; an unavailable query supplies no permission to release that ownership. A normal completion never cleans an intentionally running service. Only explicit pause or finish requests cleanup.

Messages are streamed and finalized by item ID. Recovery includes the final responses following the matching delivery, in conversation order. Response text is preserved up to 4 MiB; overflow is reported explicitly instead of displaying a final tail as the whole response. The original Codex thread remains the source for larger messages.

## Delivery reconciliation

The manager persists the exact output of `opsDeliveryPrompt` before sending it. Its visible marker contains the delivery ID and a digest of the unmodified prompt. `clientUserMessageId` carries the same ID, but the implementation does not assume this field supplies server-side deduplication.

Reconciliation reads metadata and paginates `thread/turns/list` with full items. The installed CLI does not implement `thread/items/list`; the adapter does not depend on it. Only an exact user-message match proves acceptance. Assistant quotations, incomplete history, repeated cursors and changing snapshots cannot prove non-delivery.

`accepted` means the input was admitted, not that execution succeeded. A missing marker produces no permission to replay an ambiguous mutation: `safeToRetry` remains false. A steer rejected by a definite turn precondition can fall back once to an idle start after reconciliation. Transport timeouts and disconnects never use that fallback. Runtime, configuration and target failures before input submission carry `deliveryState: "not_sent"`. Unidentified initial thread allocation stays unknown rather than allocating another thread.

## Goal-owned tools

Only supplied tool definitions with executable trusted closures are advertised. Incoming calls must match the bound thread, active turn and tool name. Persisted thread/turn events are flushed before invoking the closure. The manager receives the server's `callId`, thread and turn IDs separately from model arguments and journals schedule mutations by that identity. It supplies no cross-goal selector to these tools.

The private asynchronous RPC request hook retains default denial for account clients. Duplicate in-flight server request IDs share one response; conflicting reuse is rejected. Server diagnostics are not forwarded through RPC errors.

The CLI persists dynamic tool definitions when a thread is created. The validated resume schema cannot replace that set. Unreleased development-fixture threads created before the goal QA tools were added may therefore lack them; Ops must not silently replace the original thread or infer tool availability from a normal resume acknowledgement. New production goals register the complete tool set at creation. QA availability for an older unverified definition set remains unconfirmed until established by an actual bound tool call.

## Goal-owned QA

`electron/ops-qa.cjs` reuses the public ReviewOps QA and observed-document tool schemas. Its `ops_qa_open`, `status`, `state`, `capture`, input, navigation, document, release and close tools do not accept project, client, QA session or window IDs from the model. The trusted goal supplies its registered project, dataset epoch/birth, Codex thread/turn and lifecycle token. A folder-only goal must select a registered project before using project QA. Each bridge derives its own client identity and keeps its lease in memory; a restarted bridge never adopts a persisted lease.

The manager journals the original call ID and canonical argument digest before acquiring a window or sending GUI input, then persists the outcome before replying. Completed duplicates return their original receipt. Prepared or unknown operations never replay; a changed document or uncertain input must be observed again using a new request. Pause, finish, target replacement and disconnect invalidate the old lifecycle before cleanup. Cleanup releases only that bridge's captured lease and does not close another goal's window.

Failed cleanup retains the original private lease and blocks new acquisition. Explicit recovery retries those same application/client/session/project/window identities. If release already applied but its acknowledgement or receipt was lost, only a private live-service lookup proving that exact session absent can confirm cleanup; generic unavailable status and mismatched identities are insufficient. No current or other goal's lease is adopted during recovery.

The QA queue rechecks the trusted guard after readiness waits and immediately before native input, navigation, reload, close and project-window creation. Embedded browser operations preserve the browser ID and observed document generation. Matching releases for an input already pressed remain addressed to the original contents even when the goal changes.

A capture returns its original PNG to Codex as an app-server `inputImage` content item, alongside JSON metadata in a separate `inputText` item. It is never encoded as a block of text for the model. The transient PNG is limited to 2 MiB so the returned item and any server echo fit the bounded RPC frame. Original bytes are stored privately below the goal's capture directory with a UUID filename, hash, size and dimensions. Product history stores only that reference, binding and bounded metadata, including CSS conversion scales. A duplicate capture rechecks and returns the same bytes; missing or changed evidence fails without taking a new picture. Bulk image bytes are not copied into goal history or forwarded as SSH credentials.

Logical backups retain the goal's QA receipts and capture references, rather than embedding this private PNG cache. Copying the complete application data directory retains the cache too. After a backup is moved without its original cache, duplicate image retrieval reports unavailable evidence and takes no replacement screenshot.

## SSH targets

`ssh.inspectAppServerTarget` resolves the directory through SFTP using existing approved connection settings. `ssh.openAppServer` rechecks the server identity and canonical path before starting a persistent stdio app-server. Remote paths use POSIX rules and are never passed to local filesystem canonicalization. Local and SSH authentication stay in their existing runtime environments; the adapter copies no login files.

Direct SSH binding identity includes the verified host-key fingerprint and account. Its directory lock identity excludes the account, so two users cannot concurrently claim the same path on that verified server. OpenSSH aliases use hostname, port and account from the connection's immutable Host/Include snapshot; the lock excludes the account. Both modes also claim a common normalized-hostname/port lock alias, so a direct connection and an OpenSSH alias resolving to that endpoint conflict. Existing strict known-hosts checks, ProxyJump handling and credential references are retained. Different unresolved DNS names or remote mounts sharing physical storage cannot be inferred as equivalent by this fallback identity.

## Focused checks

Transport and SSH checks use owned fixtures. Account-backed checks are explicitly opt-in:

```sh
node --test tests/ops-session.test.cjs tests/ops-qa.test.cjs tests/ops-protocol.test.cjs tests/codex-backend-rpc.test.cjs
node --test --test-name-pattern='Ops' tests/ssh.test.cjs tests/config-ssh.test.cjs
node scripts/e2e-ops-session.mjs --real-codex
node scripts/e2e-ops-session.mjs --real-codex --ssh
node scripts/e2e-ops-execution-ui.mjs --real-codex
node scripts/e2e-ops-execution-ui.mjs --real-codex --stop-only
```

The real-CLI script checks same-turn steering, an actual client tool response, exact delivery history and connection restart without replay. Its SSH mode uses an owned loopback server on the same computer. The UI execution script runs the source Electron application's real main/preload/manager, independent local goal turns, a real cron minute, same-folder waiting and selected-goal interruption. Its `--stop-only` mode limits a causal rerun to two actual A/B commands: pause A and verify its non-zombie process exits before app shutdown, while B's completed model turn retains ownership of its live command. B's command then finishes naturally with its exact fixture result, and the real metadata watcher releases ownership after proving empty terminals. It uses the existing login directly, explicit workspace access settings and temporary folders. These checks do not establish installed desktop UI, separate physical-PC operation or comprehensive release QA.
